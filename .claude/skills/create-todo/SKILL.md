# Todo リスト作成

実装作業を、実装サブエージェント `implementer`（Haiku）が迷わず実行できる粒度の Todo に分解し、Markdown ファイルとして保存します。各 Todo には **依頼事項** と **完了条件** を必ず書きます。

## モード

- **新規作成**：引数が Issue 番号または依頼内容だけの場合
- **再作成**：引数に前回の Todo ファイルのパスがある場合、または `implementer` から「未完了」の報告を受けた直後の場合

## 手順

### 1. 情報を集める

1. `AGENTS.md`、`docs/requirements.md`、`docs/specifications.md` を読み、依頼に対応する仕様 ID（`F-x`・`V-x`・`H-x` など）を特定します
2. Issue 番号が指定されていれば `gh issue view <番号>` で本文を読みます
3. `.claude/rules/tdd.md` と、作業に関係する `.agents/rules/` の規約を読みます
4. `src/` の現状のコードとテストを確認し、既に実装済みの部分を把握します

仕様が曖昧・未決（TBD：T-1〜T-3 など）で推測でしか分解できない場合は、Todo を作らずにユーザーへ確認します。

### 2. Todo に分解する

分解のルールは次のとおりです。

- **1 Todo = 1 つの振る舞い**：TDD の 1 サイクル（Red → Green → Refactor）で完了できる大きさにします。目安は、変更するファイルが本体 1〜2 個とテスト 1 個まで
- **依存順に並べる**：前の Todo が終わっていないと着手できないものは後ろに置きます
- **自己完結させる**：`implementer` は会話の文脈を知りません。対象ファイルのパス、クラス名・メソッド名、参照すべき仕様 ID と規約ファイルを具体的に書きます
- **完了条件は客観的に検証できるものだけ**：「適切に実装されている」のような主観的な条件は書きません。次のような、コマンドやファイルの内容で白黒つく条件にします
  - `./mvnw test -Dtest=クラス名` が成功する
  - `@DisplayName` の先頭に `[V-2]` を付けたテストが存在し、Given-When-Then で書かれている
  - テストを先に書き、アサーションで失敗（RED）することを確認した
  - 最後の Todo には必ず「`./mvnw test` で全テストが成功する」を含める
- スコープ外（`AGENTS.md` の「スコープ外」）の作業や、新しい依存ライブラリの追加を Todo に含めません

### 3. ファイルに保存する

保存先は `.claude/todos/` です（ディレクトリがなければ作成します）。

- 新規作成：`.claude/todos/<Issue番号>-<概要>-v1.md`（例：`.claude/todos/12-input-validation-v1.md`）
- 再作成：版番号を 1 つ上げた新しいファイル（`-v2.md`、`-v3.md`…）を作り、前の版は削除せず残します

書式は次のテンプレートに従います。チェックボックスは **Todo 本体の行だけ** に付け、完了条件は通常の箇条書きにします（`implementer` が Todo 単位でチェックを付けるため）。

```markdown
# Todo: <作業タイトル>

- Issue: #<番号>
- ブランチ: <prefix>/<issue番号>-<概要>
- 版: v1
- 対象仕様: V-1, V-2
- 作成日: YYYY-MM-DD

## 前提

- 読むべきドキュメント・規約：`docs/specifications.md` 4.2 節、`.claude/rules/tdd.md`、`.agents/rules/test.md`
- 実装上の注意：<誤りやすい点・既存コードとの関係など>

## Todo

- [ ] **T1. <やることを一文で>**
  - 依頼事項：<何を、どのファイルに、どう実装するか。関係する仕様 ID>
  - 対象ファイル：`src/main/java/...`、`src/test/java/...`
  - 完了条件：
    - <検証可能な条件 1>
    - <検証可能な条件 2>
- [ ] **T2. ...**
  - 依頼事項：...
  - 対象ファイル：...
  - 完了条件：
    - ...

## 実行ログ

<!-- implementer が試行結果（失敗理由・リトライ回数）を追記する欄。作成時は空のままにする -->
```

### 4. 再作成モードの追加ルール

前回の Todo ファイルと `implementer` の未完了報告を読み、失敗の原因に応じて Todo を作り直します。

- 完了済み（`[x]`）の Todo は、新しい版にも `[x]` のまま引き継ぎます
- 失敗した Todo は、原因に合わせて次のいずれかで見直します
  - 大きすぎた → より小さな Todo に分割する
  - 情報が足りなかった → 依頼事項に具体的なヒント（使う API、参考にする既存コード、期待値の例）を足す
  - 完了条件が誤っていた・検証できなかった → 仕様を根拠に完了条件を直す（仕様と異なる期待値には変えない）
- `## 前提` に「前回（v<N>）の失敗理由」と「今回の変更点」を追記します
- 失敗の原因が仕様の曖昧さ・矛盾、または新しい依存ライブラリの必要性にある場合は、再作成せずにユーザーへ確認します
- 再作成は **最大 2 回**（v3 まで）です。v3 でも未完了の報告を受けた場合は、再作成せずにユーザーへ確認します。その際は各版の失敗理由と、残っている Todo を報告します

### 5. 報告する

呼び出し元（メインエージェント）へ次を報告します。

- 作成した Todo ファイルのパスと版
- Todo の件数と一覧（1 行ずつ）
- 対象の仕様 ID

## 作成後の流れ（メインエージェント向け）

1. Agent ツールで `subagent_type: "implementer"` を指定し、Todo ファイルのパスを渡して実装を依頼します
2. `implementer` から **完了報告** を受けたら、Todo ファイルの全チェックが `[x]` になっていることと `./mvnw test` の結果を自分でも確認し、開発フローの次の手順（全テスト・Codex レビュー）へ進みます
3. コミットは `implementer` が Todo 1 件ごとに行います（Todo ファイルも同じコミットに含まれます）。新規作成・再作成した Todo ファイル自体は、`implementer` に依頼する前にメインエージェントがコミットします
4. `implementer` から **未完了報告** を受けたら、このスキルを再作成モードで実行して Todo リストを作り直し、新しい版のファイルで再度 `implementer` に依頼します。再作成は最大 2 回で、v3 でも未完了ならユーザーへ確認します
