# TDD（テスト駆動開発）ルール

本プロジェクトの実装は、すべて TDD（Red → Green → Refactor）で進めます。テストより先にプロダクションコードを書いてはいけません。

## サイクル

### 1. Red：失敗するテストを書く

- 実装したい振る舞いを 1 つだけ選び、それを検証するテストを書きます
- テストを実行し、**意図した理由で失敗（RED）すること**を確認します
  - コンパイルエラーだけで終わらせず、必要なら空のクラス・メソッドを用意して「アサーションで失敗する」状態まで持っていきます
  - 想定外の理由で失敗した場合は、テストの書き方を見直します
- 仕様に対応するテストには、テスト名や `@DisplayName` に仕様 ID（例：`V-2`、`H-4`）を含めます

### 2. Green：最小限の実装でテストを通す

- RED を確認してから、テストを通すための**最小限**のコードだけを書きます
- 今のテストが要求していない機能・汎用化・最適化は入れません
- テストを再実行し、**GREEN になること**を確認します

### 3. Refactor：振る舞いを変えずに整理する

- 重複の除去、命名の改善、責務の分離などを行います（テストコードも対象）
- リファクタリングのたびにテストを実行し、**RED に戻らないこと**を確認します
- リファクタリング中に新しい振る舞いを追加してはいけません。追加したくなったら、次のサイクルの Red から始めます

## テストの実行コマンド

```bash
# 作業中のテストクラスだけを素早く実行
./mvnw test -Dtest=クラス名

# 特定のテストメソッドだけを実行
./mvnw test -Dtest=クラス名#メソッド名

# 全テストの実行（サイクルの区切り・実装完了時）
./mvnw test
```

## 禁止事項

- RED を確認せずに実装へ進むこと
- テストを通すために、テストの期待値を仕様と異なる値へ書き換えること
- 失敗するテストを `@Disabled` やコメントアウトで回避すること
