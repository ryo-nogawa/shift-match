# コメント

## 基本方針

- コメントには「何をしているか」ではなく「なぜこの実装にしたか」を記載する
  - 「何をしているか」はコード自体や `{@link}` を参照すればわかるため、コメントに重複して書く必要はない
- 「なぜ」を書くのは、コードや Javadoc を読んだだけでは理由が読み取れない箇所に限る（下記の対象）
- 理由が自明な箇所や、名前・Javadoc で意図が伝わる箇所には、コメントを付けない

## 「なぜ」を書く対象

次のいずれかに当てはまる場合は、理由をコメントで補う。

- 一見遠回りに見える実装（例：総当たりではなく動的計画法にした理由）
- 既知の制約や不具合への回避策
- 外部仕様や要件定義の ID に基づく処理（例：`H-2` のため）
- 変えると挙動が壊れやすい箇所（例：同点時に `<=` ではなく `<` で更新する理由）

## 重要度の目安（レビュー用）

- 対象の箇所に理由がなく、誤読や誤修正のおそれがある：SHOULD
- 上記以外で、理由のコメントがない、または「何をしているか」だけのコメント：WANT
- コメントに関する指摘は MUST にしない

## 記載例

```java
// NG：「何をしているか」を説明しているだけ
// カウンタをインクリメントする
counter.incrementAndGet();

// OK：「なぜこの実装にしたか」を説明している
// 複数スレッドからの同時アクセスでカウントがずれないよう、AtomicInteger でインクリメントする
counter.incrementAndGet();

// コメント不要：名前とコードから理由まで明らか
return employees.size() >= MAX_EMPLOYEES;
```
