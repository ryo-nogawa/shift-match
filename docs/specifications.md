# 要件定義

## 1. 本書の目的

[要求定義](requirements.md) の要求を満たすための仕様を定義します。実装とテストは本書を根拠として行います。

## 2. 割り当て枠の導出

枠は要求定義の制約条件（C-1〜C-5）から一意に決まります。仕様変更時に前提を見失わないよう、導出過程を記録します。

1. **開始時刻の候補**：C-1・C-2 より、開始時刻は 8〜12 時の 5 通りです
2. **出勤者の上限**：どの開始時刻でも 12:00〜17:00 は勤務時間に含まれるため、この時間帯の人数は出勤者数と一致します。C-3 より **出勤者は最大 4 人** です
3. **朝の下限**：8:00〜9:00 に勤務できるのは 8 時開始者のみのため、**8 時開始が 2 人以上** 必要です
4. **夜の下限**：20:00〜21:00 に勤務できるのは 12 時開始者のみのため、**12 時開始が 2 人以上** 必要です
5. **結論**：3・4 より最低 4 人、2 より最大 4 人となり、構成は次の一通りに定まります

| 枠   | 勤務時間       | 人数         |
| ---- | -------------- | ------------ |
| 早番 | 8:00 〜 17:00  | 2 名（固定） |
| 遅番 | 12:00 〜 21:00 | 2 名（固定） |

これにより、時間帯ごとの人数は 8〜12 時が 2 名、12〜17 時が 4 名、17〜21 時が 2 名となり、C-3 を満たします。ただし休憩中の人は人数に数えないため、C-3 を保つには休憩を 12:00〜17:00 に取り、同時に休憩するのは 2 名までとする必要があります。

休憩はアプリが自動で割り当てます（T-1 決定済み）。休憩は 1 人 1 時間・1 時間刻みとし、1 人ずつ順番に取ります（4 名で計 4 時間）。基本は 13:00〜17:00 の間で回します。割り当ては次のとおりです。

| 対象        | 休憩時刻                                |
| ----------- | --------------------------------------- |
| 早番の 2 名 | 入力順に 13:00〜14:00、14:00〜15:00     |
| 遅番の 2 名 | 入力順に 15:00〜16:00、16:00〜17:00     |

## 3. 機能一覧

| ID  | 機能         | 概要                                     |
| --- | ------------ | ---------------------------------------- |
| F-1 | 希望入力     | 従業員名と希望を画面から入力します       |
| F-2 | 入力行の追加 | 入力欄を動的に追加します                 |
| F-3 | シフト作成   | 最適な割り当て案を 1 つ算出します        |
| F-4 | 結果表示     | 算出した案を画面に表示します             |
| F-5 | 不成立の通知 | 条件を満たす案がない場合、その旨を表示します |
| F-6 | 入力行の削除 | 入力行を削除します（最低 1 行は残します） |

## 4. 入力仕様

### 4.1 入力項目

| 項目     | 必須 | 値                                                   |
| -------- | ---- | ---------------------------------------------------- |
| 従業員名 | 必須 | 文字列。画面内で一意                                 |
| 早番希望 | 必須 | ◎ 希望する（優先）／○ 可能／× 不可（割り当てない） |
| 遅番希望 | 必須 | 同上                                                 |

### 4.2 入力チェック

| No  | 内容                                           | 挙動                                   |
| --- | ---------------------------------------------- | -------------------------------------- |
| V-1 | 従業員名が未入力の行                           | 処理対象から除外します（エラーとしません） |
| V-2 | 従業員名の重複                                 | 該当行を示してエラーメッセージを表示します |
| V-3 | 有効な行の早番・遅番希望が ◎／○／× 以外（未選択を含む） | 該当項目にエラーを表示し、算出しません |
| V-4 | 有効な従業員が 4 名未満                        | 算出せず、不成立として扱います         |

チェックはサーバー側で、V-1 → V-4 の順に行います。

## 5. 割り当てルール

### 5.1 ハード制約

すべて満たす組み合わせのみを案として扱います。

| ID  | 条件                                          |
| --- | --------------------------------------------- |
| H-1 | 早番にちょうど 2 名を割り当てます             |
| H-2 | 遅番にちょうど 2 名を割り当てます             |
| H-3 | 1 人が割り当てられる枠は、1 日に最大 1 つです |
| H-4 | × と申告された枠には割り当てません            |

### 5.2 評価（ソフト制約）

> **スコア = 割り当てられた 4 名のうち、その枠を ◎ と申告していた人数**（0〜4 点）

スコアが最大の案を採用します。

### 5.3 同点時の決定方法

スコアが同じ案が複数ある場合は、次の順で列挙したときに **最初に最大スコアに到達した案** を採用します（同点では更新しません）。

1. 早番 2 名の組を、入力順のインデックスの辞書順（(0,1), (0,2), …）で列挙します
2. 各組について、残りの従業員から遅番 2 名の組を同じ順序で列挙します

結果として、早番は入力画面の上にいる人ほど優先されます。

### 5.4 探索方法

全組み合わせを総当たりで評価します。最適化ライブラリは使用しません。

- 組み合わせ数は n 人で `C(n,2) × C(n-2,2)` 通りです（n = 10 で 1,260 通り、n = 20 で約 29,000 通り）

## 6. 不成立時の仕様

ハード制約を満たす案が 1 つもない場合、案を出力せず、不成立である旨を表示します。原因（早番の希望者不足など）の分析・表示は行わず、不成立の事実のみを示します（T-3 決定済み）。

不成立の判定は、総当たりの結果が 0 件であることで行います。枠ごとの可能人数を独立に数える方法は、1 人が両方の枠に ○ を付けられるため誤判定します（例：早番可 2 名・遅番可 2 名でも、同一の 2 名であれば成立しません）。

## 7. 出力仕様

| 項目     | 内容                             |
| -------- | -------------------------------- |
| 早番     | 割り当てられた 2 名の勤務時間（08:00〜17:00）・氏名・休憩時刻 |
| 遅番     | 割り当てられた 2 名の勤務時間（12:00〜21:00）・氏名・休憩時刻 |
| スコア   | 満たした ◎ の数（0〜4）          |
| 未出勤者 | 割り当てられなかった従業員の一覧 |

成立時はこれらの項目を表形式で表示します。割当結果の表の列は「勤務時間・氏名・休憩」の順とし、勤務時間は休憩と同じ 24 時間表記・前 0 埋め（`08:00〜17:00`）で各行に表示します。「早番」「遅番」の名称は画面に表示しません（時間軸のバー表示は採用しません。T-2 決定済み）。

## 8. 画面仕様

1 画面で完結します。上部に入力表と操作ボタン（「行を追加」「シフトを作成」）、下部に結果（割り当て結果または不成立メッセージ）を配置します。

入力行は JavaScript で動的に追加します。Spring MVC でリスト形式のフォームを受け取るため、`name` 属性には連番のインデックスを付与します。

```html
<input name="employees[0].name" />
<input name="employees[0].earlyWish" />
<input name="employees[0].lateWish" />
```

**インデックスに欠番があると正しくバインドできません。** 行の削除機能を実装する場合は、削除後に必ずインデックスを振り直してください。

行の削除（F-6）は、各入力行の「削除」ボタンで行います。入力表が 1 行のときは、その行の削除ボタンを無効にし、最低 1 行を残します。削除後は `name` 属性のインデックスを 0 から連番に振り直します。

## 9. 非機能要件・技術構成

| 項目       | 内容                                                                    |
| ---------- | ----------------------------------------------------------------------- |
| 状態管理   | 状態を保持しません。入力・計算・出力が 1 リクエストで完結します         |
| データ保存 | 行いません。画面を再読み込みすると入力内容は失われます                  |
| 性能       | 従業員 20 名程度までを想定します。この規模では応答時間は問題になりません |
| 認証・同時利用 | 認証は実装せず、同時利用も想定しません                              |
| 技術       | Java 25 / Spring Boot 4.1.1 / Thymeleaf + 素の JavaScript / Maven       |

データベースを使用しないため、`spring-boot-starter-data-jpa` や H2 の依存は追加しません。
